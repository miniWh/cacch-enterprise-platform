## 二、必须先纠正的 4 个错误

这 4 处若不修正，部署必然失败或存在隐患。

### ❌ 错误 1：Tomcat 版本写错（**会导致启动失败**）

README 第 8 章与 `CacchEnterpriseApplication.java` 类注释均写「Tomcat 10.1.x」。

- 项目实际为 **Spring Boot 4.0.9**（pom 实测），基于 **Jakarta EE 11 → Servlet 6.1**
- Tomcat 10.1.x 仅实现 **Servlet 6.0**，加载时会报 `NoSuchMethodError` / 类加载失败
- ✅ **必须安装 Tomcat 11.0.27**（实测阿里云镜像可用版本为 v11.0.26 / v11.0.27）

需同步修正：README 技术栈表、第 8 章、`CacchEnterpriseApplication` 类注释。

### ❌ 错误 2：README 的 Nginx 示例会转发失败

README 第 8.3 节示例：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080/cacch-enterprise-web/;   # 会剥离 /api 前缀
}
```

但实测 Controller 路径**自带** `/api` 前缀：

```
PATH_LOGIN   = /api/v1/auth/login
PATH_USERS   = /api/v1/system/users
PATH_MENUS   = /api/v1/system/menus
PATH_DEPTS   = /api/v1/system/depts
```

`proxy_pass` 带 URI 时会把 `/api/v1/auth/login` 改写为 `/cacch-enterprise-web/v1/auth/login`，后端 404。

✅ 正确做法：**War 包命名为 `ROOT.war`（context path = `/`），Nginx 原样转发不剥离前缀**。

### ❌ 错误 3：prod 配置仍是占位符

`application-prod.yml` 中两处必须外置覆盖，否则 JWT 无法签名、前端跨域被拦：

```yaml
jwt-secret: CHANGE_ME_VIA_EXTERNAL_CONFIG   # ← 必须替换
cors.allowed-origins: https://your-prod-domain  # ← 必须改为 http://10.80.62.200
```

### ❌ 错误 4：JVM 堆参数会导致 OOM

README 建议 `-Xms1g -Xmx2g`。本机总内存仅 3.5 Gi，叠加 Tomcat 自身开销（Metaspace + 线程栈 + 堆外）实际占用可达 2.5 G+，再算上 OS 与 Nginx，**必然 OOM 或疯狂 swap**。

✅ 本机调整为：**`-Xms512m -Xmx1024m -XX:MaxMetaspaceSize=256m`**

## 五、打包与部署方式

### 5.1 采用 Skinny War（依赖外置，解决"每次打包过大"）

常规 War 会把 Spring 全家桶 + MyBatis-Plus + JJWT 等全部打进 `WEB-INF/lib`，产物 **80~100 MB**，每次发版都要重新压缩 100 MB。

改为**依赖外置到 Tomcat 公共类库**，War 只保留业务 class 与资源：

| 对比项 | 普通 War | Skinny War（采用） |
| --- | --- | --- |
| 产物大小 | 80~100 MB | **1~3 MB** |
| 每次打包耗时 | 数十秒（压缩 100 MB） | **1~2 秒** |
| 依赖变更时 | 无感 | 需重新同步 lib（低频） |

`cacch-enterprise-web/pom.xml` **已配置完成**（2026-10-30）：

- `maven-war-plugin`：`packagingExcludes=WEB-INF/lib/*.jar`，War 内不含依赖
- `maven-dependency-plugin`：`copy-dependencies` 把 runtime 依赖导出到 `${tomcat.lib.dir}`
- `provided` 作用域（如 `spring-boot-starter-tomcat`）不导出，由 Tomcat 自身提供

本地构建默认导出到 `target/tomcat-lib`（不污染系统）；服务器构建通过参数覆盖到 Tomcat 公共类库：

```bash
# 首次 / 依赖变更时：同步依赖到 Tomcat lib，并打业务 War
mvn clean package -DskipTests -Dtomcat.lib.dir=/opt/cacch/tomcat/lib

# 日常发版（业务代码变更、依赖未变）：跳过依赖导出，秒级出包
mvn clean package -DskipTests -Dmdep.skip=true
```

> ⚠️ **发版检查项**：改动 `pom.xml` 依赖后必须重新执行带 `-Dtomcat.lib.dir=...` 的全量构建，否则运行时报 `NoClassDefFoundError`。

### 5.1.1 构建位置：服务器构建 vs 本地构建（2026-10-30 实测）

Skinny War 把产物压到 **120 KB**，使得"本地构建 + 上传"变得非常划算：

| 方式 | 命令 | 耗时（实测） | 适用场景 |
| --- | --- | --- | --- |
| 服务器构建 | `bash /opt/cacch/src/deploy/deploy.sh` | 8~25 秒 | 依赖变更（必须）；服务器上直接改代码 |
| **本地构建上传** | `bash deploy/07-build-local-backend.sh` | 首次 43 秒（含下载依赖），之后约 15 秒 + 上传 1 秒 | **日常业务代码发版，推荐** |

本地工具链（实测可用，无需额外安装）：

- JDK **21.0.10**（`D:\Software\Java\jdk21.0.10_7`）
- Maven **3.9.11**（IntelliJ IDEA 自带：`D:\Software\IntelliJ IDEA 2025.3.3\plugins\maven\lib\maven3`）

脚本会自动探测这两者，无需配置 PATH。已实测：本地构建的 War **119 KB、War 内 0 个依赖 jar**，
上传后由 `/opt/cacch/install-war.sh` 完成备份→停→部署→启→校验，服务启动 **6 秒**，接口全部正常。

> ⚠️ 本地构建用 `-Dmdep.skip=true` 跳过依赖导出，**不会**同步 `tomcat/lib`。
> 因此改了 `pom.xml` 依赖时请改用服务器 `deploy.sh --full`。

### 5.2 Context path 处理：**部署时重命名为 `ROOT.war`**

因为后端 Controller 路径自带 `/api` 前缀、Nginx 需原样转发，应用必须挂在根路径 `/` 上。不修改 `finalName`，而是在**拷贝时改名**即可：

```bash
cp cacch-enterprise-web/target/cacch-enterprise-web.war \
   /opt/cacch/tomcat/webapps/ROOT.war
```

这样 context path 就是 `/`，Nginx 侧无需任何路径改写。若沿用原名 `cacch-enterprise-web.war`，则 Nginx 必须显式补回前缀：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080/cacch-enterprise-web/api/;   # 备选写法
}
```

两者等价，**推荐 ROOT.war**，配置更简洁、不易出错。

### 5.3 Tomcat jar 扫描优化（Skinny War 下必需）

依赖放进 Tomcat `lib` 后，Tomcat 启动会逐个扫描这些 jar（TLD / Spring SCI），2 核机器上会显著拖慢启动。`conf/catalina.properties` 增加：

```properties
tomcat.util.scan.StandardJarScanFilter.jarsToSkip=*.jar
tomcat.util.scan.StandardJarScanFilter.jarsToScan=spring-web-*.jar,cacch-*.jar
```

## 六之三、本地构建发版 + systemd 重启风暴修复（2026-10-30 14:51~14:57 实测）

### ✅ 本地构建上传：可行，已实测

后端与前端一样改为**本地构建、只上传产物**。新增两个脚本：

| 脚本 | 运行位置 | 职责 |

| `deploy/install-war.sh` | 服务器 `/opt/cacch/` | 备份 → 停 → 改名 ROOT.war → 启 → 校验 systemd 状态 |
| `deploy/sudoers-cacch` | 服务器 `/etc/sudoers.d/cacch` | felix 对 Tomcat 服务与 `restorecon` 的**限定命令**免密 sudo |

实测结果：本地构建 43 秒（首次含下载依赖）→ War 119 KB / 内含 0 个 jar → 上传 → 启动 6 秒 → 首页/接口 200、鉴权 40100、ERROR 0。

### ⚠️ 过程中发现并修复的一个严重问题：游离 JVM + 重启风暴

首版 `install-war.sh` 用 `systemctl list-unit-files | grep` 判断是否由 systemd 托管，
该探测在非交互 SSH 下失败 → 脚本 fallback 到 `startup.sh` 直启 → 拉起**游离 JVM（PID 343250，PPID=1）**
占住 8080；随后 systemd 按 `Restart=on-failure` 反复尝试启动，每次都因端口冲突失败（NRestarts=4）。
表现为**"接口访问正常，但服务其实在崩溃循环"**，极具迷惑性。

修复三项：

1. **发版脚本强制走 systemd**，判断依据改为 unit 文件是否存在（不再依赖 systemctl 查询），
   并增加**端口预检**与残留进程清理，杜绝游离 JVM。
2. **`cacch-tomcat.service` 补 `PIDFile=/opt/cacch/tomcat/tomcat.pid`**
   —— `Type=forking` 缺 PIDFile 时 systemd 认错主进程，`stop` 只杀掉 startup.sh 的 shell。
   同时加 `StartLimitIntervalSec=300` / `StartLimitBurst=5` 限制重启风暴。
3. **配置限定命令的免密 sudo**（`deploy/sudoers-cacch`），避免脚本因等待密码而静默走错分支。

修复后复测：`Active: active (running)`、`Main PID` 正确指向 java、接口 200、ERROR 0，
再次跑完整发版流程 `systemd 状态：active`，闭环稳定。

## 八、风险与建议

1. **内存是最大约束**：2 核 3.5 Gi 属于"能跑起来但没有余量"。生产环境建议至少 **4 核 8 Gi**。当前配置下禁止再部署其他应用。
2. **令牌有效期偏长**：`access-token-expire: 43200`（12 小时）对管理后台偏长，建议评估下调至 7200（2 小时）。
3. **prod 配置含明文口令**：`application-prod.yml` 中 DB/Redis 口令为明文。建议改用环境变量注入（`REDIS_PASSWORD` 等），配置文件权限设 `600`。
4. **WebSocket 尚未实现**：`websocket` 包为空，README 中的 `/ws/` 代理规则当前无需配置，待实现后再补。
5. **PostgreSQL 12.22 已 EOL**：官方 2024-11 起停止支持。当前为既有外部资产、本次不动，但长期建议规划升级。
6. **Tomcat lib 依赖同步**：Skinny War 模式下，若 `pom.xml` 依赖变更却未重新执行带 `-Dtomcat.lib.dir=/opt/cacch/tomcat/lib` 的全量构建，会报 `NoClassDefFoundError`。**发版前请确认「是否改过 pom」**。
7. **服务器凭证**：部署所用账号口令建议尽快改为 SSH 密钥认证，并避免口令在文档/会话中留存。
